Artemis disk accessor

VHDX parser and format

How Artemis opens a VHDX and turns it into a guest disk. The parser lives under forensics/src/accessor/disk/vhdx and follows Microsoft MS-VHDX. libyal’s libvhdi notes are the references cited in the source comments. This describes the accessor-vhdx branch.

Version 1 scope. Fixed and dynamic disks are read. Differencing disks are rejected. A non-empty log is reported as pending_log and is not replayed. A damaged BAT entry fails the open. The virtual disk may be up to 64 TiB.

Module map

vhdx/mod.rs declares the modules. format.rs turns DiskFormat::Vhdx into a DiskReader::Vhdx. image.rs is the path wrapper. reader.rs is the only type that implements Read and Seek for the guest.

First megabyte of the file

MS-VHDX 2.2 fixes the layout of the first 1 MiB. Everything the parser needs to find the BAT and the metadata is inside it. VhdxReader::open refuses a file shorter than 320 KiB, which is the end of the second region table.

VhdxReader::open in reader.rs is the whole parse. Each later step uses only what the previous step returned. A failure here is a volume error and the image does not open.

File identifier

MS-VHDX 2.2.1 and libyal section 2. The first 8 bytes are the little-endian signature 0x656c696678646876, the ASCII bytes vhdxfile. parse_header in identifier.rs checks that with nom_u64, then takes the next 512 bytes as a UTF-16LE creator string. extract_utf16_string turns that into VhdxReader::creator. The rest of the 64 KiB identifier area is reserved and is not parsed.

Image header

MS-VHDX 2.3.1. Two copies, at 64 KiB and 128 KiB. parse_image_header requires 4096 bytes, signature 0x64616568 (“head”), format version 1, and log version 0. vhdx_crc32c zeros bytes 4 through 7 and computes the Castagnoli CRC the spec stores in the checksum field. A mismatched checksum rejects that copy.

active_head keeps the copy with the greater sequence number. One invalid copy is ignored. Both invalid is an error. Equal sequence numbers are an error, which matches the spec and rejects a header pair that was copied mid-update. The fields kept on VhdxHeader are sequence, file_write, data_write, log, log_version, version, log_length, and log_offset. image_metadata copies the three GUIDs out as strings.

has_pending_log is true when the log GUID is not nil. MS-VHDX 2.3.1 says a zero log GUID means the log is empty and must not be replayed. active_head emits a tracing warning and still returns the header. Nothing in open replays log entries. The flag is published as VhdxImageMetadata.pending_log.

Region table

MS-VHDX 2.4. Copies at 192 KiB and 256 KiB, each 64 KiB. parse_region_table checks signature 0x69676572 (“regi”), the same CRC as the header, a reserved field of zero, and an entry count of at most 2047. Each entry is 32 bytes: GUID, file offset, length, flags. parse_entry requires a 1 MiB aligned offset at or past 1 MiB, a non-zero 1 MiB aligned length, no overflow, and no duplicate GUID. The required bit is flags bit 0. Any other flag bit is an error. check_overlaps rejects intersecting ranges.

active_regions requires the two known regions and returns them on VhdxRegionTable. An unknown region is accepted when its required bit is clear and rejected when the bit is set. If both copies parse and differ, the file is rejected. One bad copy is ignored.

Metadata region

MS-VHDX 2.6. open reads min(region length, 1 MiB) from the metadata file offset and passes that buffer to parse_metadata. The table itself occupies the first 64 KiB. Item values start at offset 65536 or later, which is why a 64 KiB read is not enough.

The signature is 0x617461646174656d (“metadata”). The reserved 16-bit field must be zero. At most 2047 entries. Each entry is a GUID, offset, length, and flags. parse_entry rejects a zero length, an offset inside the 64 KiB table, a range past the buffer, a duplicate GUID, a non-zero reserved field, and flag bits outside IsUser, IsVirtualDisk, and IsRequired.

Required items

required_item fails the open if any of these five GUIDs is missing. is_required_virtual_item requires IsVirtualDisk and IsRequired on each of them. File parameters are the exception: flags equal to IsRequired alone (0x4) are accepted, which is what QEMU writes. IsUser and IsVirtualDisk are independent. An entry may set both, one, or neither.

Derived values

Block size must be a power of two from 1 MiB through 256 MiB. Virtual size must be non-zero, at most 64 TiB, and a multiple of the logical sector size. LeaveBlocksAllocated comes from bit 0 of the file-parameters flags and means the disk is fixed. Bit 1, HasParent, is a second differencing check and is rejected.

chunk_ratio implements the spec definition. One sector-bitmap block describes 223 logical sectors, so the chunk size is 223 times the logical sector size. The chunk ratio is how many payload blocks fit in that chunk:

chunk_ratio = (1 << 23) * logical_sector_size / block_size

For 512-byte sectors and 1 MiB blocks the ratio is 4096, and one chunk is 4 GiB of guest data. For 512-byte sectors and 32 MiB blocks the ratio is 128.

Block allocation table

MS-VHDX 2.5 and 2.5.1. libyal section 6. The BAT is an array of 64-bit entries. split_entry takes the low 3 bits as the state, the next 17 bits as reserved (must be zero), and the high 44 bits as FileOffsetMB. Masking with !0xfffff leaves the byte offset, because the field is already in 1 MiB units shifted 20 bits.

The layout is the same for fixed and dynamic disks. A sector-bitmap entry follows every chunk except the last one. The last entry is the last payload block. bat_entry_count is:

payload_blocks + floor((payload_blocks - 1) / chunk_ratio)

payload_blocks is virtual_disk_size divided by block_size, rounded up. parse_bat walks that pattern once. There is no separate path for LeaveBlocksAllocated. A bitmap entry is read only while payload blocks remain after the chunk.

Sector bitmap states

parse_bitmap runs on the entries between chunks. State 0 is not present and its offset is ignored. State 6 is present: the parser checks a 1 MiB range with validate_present and then discards the bitmap, because a non-differencing disk has no parent to consult. The spec marks state 6 invalid for fixed and dynamic files. Any other state is an error.

How much of the BAT is read

bat_table_bytes returns the entry count times 8. It rejects a table larger than 67,125,247 entries, which is 537,001,976 bytes. That is a 64 TiB disk with 1 MiB blocks and 512-byte sectors: 67,108,864 payload entries plus 16,383 bitmap entries. open reads min(region length, that size) from the BAT file offset. parse_bat then requires the buffer to be at least that long.

validate_present checks each present payload or bitmap block. The file offset must be at least 1 MiB, the range must fit in the file, and it must not overlap the metadata region, the BAT region, or the log. Those occupied ranges come from occupied_ranges. After the walk, check_present_overlaps sorts the present ranges by file offset and compares neighbors. Two sorted ranges overlap only when an adjacent pair overlaps.

VhdxBat stores one PayloadBlock per payload block, in guest order. map_offset divides the guest offset by the block size, clips the returned length at the end of the block and at the end of the virtual disk, and returns VhdxMapping::Zero or VhdxMapping::Data.

Log

MS-VHDX 2.3.2 and 2.3.3 describe the log and require replay before guest I/O when the log GUID is not zero. This parser does not implement replay. log_range still checks the geometry: a zero log_length means there is no region. Otherwise the offset and length must be 1 MiB aligned, the offset must be at least 1 MiB, the range must fit in the file, and ranges_overlap must say it misses both the BAT and the metadata region. The log is then added to the occupied list so a payload block cannot point into it.

Guest bytes for blocks written while the log was active can differ from what the host last flushed. pending_log on the image metadata is the signal for that. The on-disk BAT and metadata are what get parsed.

Guest reads

VhdxReader implements Read and Seek. The seek position is a guest offset, not a file offset. seek_guest handles Start, Current, and End against virtual_size through checked_seek. Seeking does not move the underlying file.

read_guest stops at the end of the virtual disk. It fills the caller’s buffer by calling read_mapping once per block boundary. read_mapping asks map_offset for the current guest position. A zero mapping fills the buffer. A data mapping seeks the file to file_offset plus the offset within the block, then read_exact. file_position remembers where that read finished. The next present read skips the seek when the file cursor is already there. A failed seek or read clears file_position. A zero mapping does not, because it does not move the file.

Where the guest disk goes

VhdxDisk::new requires an absolute host path. open_reader opens the file and calls VhdxReader::open. image builds DiskImageMetadata with format, file_size, virtual_size, and DiskImageDetails::Vhdx(VhdxImageMetadata).

DiskFormat::open_reader in format.rs boxes that reader as DiskReader::Vhdx. logical_sector_size, read, and seek on DiskReader forward to it. DiskSource::inspect opens the disk, takes that sector size, and runs inspect_disk and identify_disk. NTFS and ext4 are then opened through PartitionReader at the partition’s byte offset. The scheme name is vhdx, parsed in accessor/location/scheme.rs.
